# KP ETSIP — platform foundation

The application provides local sign-in, profile preferences, portfolio and application inventory, executive insight, administration, audit and reports. MongoDB is required; there is no in-memory fallback.

**Release warning:** The full browser journey suite has not completed because the Playwright runner timed out. The production dependency audit reports high-severity React Router advisories; remediate and retest before production deployment.

## Local development

1. Start the replica set with `docker compose up -d mongo`, or supply a transaction-capable MongoDB URI and `MONGODB_DB`. For a backend running on the host, use `mongodb://127.0.0.1:27017/?replicaSet=rs0&directConnection=true` (the replica advertises the Compose-only name `mongo`). Copy `backend/.env.example` to `backend/.env`. The explicit development signing key and seed passwords are for local use only. Initial administrator: `admin@ketsip.local` / `DevAdmin-Change123!`. Other local accounts are `executive`, `leader`, `engineer`, `auditor`, `readonly` at `@ketsip.local`, with `DevDemo-Change123!`. These passwords are configurable through `SEED_ADMIN_PASSWORD` and `SEED_DEMO_PASSWORD`; seed runs only when enabled and never overwrites existing records. The administrator must change its password on first login.
2. From `backend`: create a venv, `pip install -r requirements.txt`, then `uvicorn app.main:app --reload`. Config is loaded from `.env` in that directory. Liveness: `/api/health`.
3. From `frontend`: `npm install` and `npm run dev`. Vite proxies `/api` to `http://127.0.0.1:8000`; set `VITE_PROXY_TARGET` to change it. Browser API base defaults to same origin.
4. Alternatively, copy `backend/.env.example` to `backend/.env`, then run `docker compose up --build`; browse `http://localhost:8080`. The new `mongo_replica_data` volume preserves replica data between restarts; the old `mongo_data` volume is not automatically migrated or deleted. MongoDB binds its host port to loopback, has no authentication, and is for local development only. Never expose it publicly.

For production, use HTTPS, a protected MongoDB instance, a randomly generated unique `JWT_SECRET` of at least 32 characters, strong unique seed passwords, and `ENVIRONMENT=production`; the service rejects known development credentials. Disable seeding after provisioning. Do not use the sample secrets. Restrict access to environment values and rotate secrets securely. Backend CORS is configured with `CORS_ORIGINS` (comma-separated origins). The current token is stored in localStorage; protect the application against XSS. Password changes and sign-out invalidate all previously issued tokens for that user.

## Migrating existing standalone data safely

Do not start the new replica against the old standalone's data directory and do not remove volumes. The new Compose volume is deliberately separate and starts empty. Plan downtime; stop all application writers and verify the source and target addresses, database names, credentials, MongoDB/Database Tools versions, storage capacity, and permissions. Keep the original standalone and its volume intact throughout; a single-node replica set is not a production high-availability deployment.

1. Take a consistent backup of the stopped-write source with `mongodump --uri "$SOURCE_URI" --db "$SOURCE_DB" --archive=standalone-backup.archive --gzip`. Store a protected copy elsewhere and verify the archive by restoring it to a separate disposable database. Never expose credentials in shell history or logs. The archive contains sensitive data.
2. Provision a **new, empty** replica set, wait for an elected primary, and set `SEED_ON_STARTUP=false` on the backend. Back up the target too if it is not empty; do not restore into an existing database without a separately approved migration plan.
3. Restore the archive using `mongorestore --uri "$TARGET_REPLICA_URI" --archive=standalone-backup.archive --gzip` into the same database name on the new empty replica set. Do not use `--drop`. Preserve indexes and inspect the restore output for errors. If renaming, use explicit `--nsFrom`/`--nsTo` mappings and verify all namespaces.
4. Before cutover compare source and destination collection counts, indexes, representative records and references (including user portfolio assignments and application portfolio IDs), and audit history. Check a transaction and login against the target, with a disposable account or restored test copy. Resolve duplicate-key/index problems before enabling the application. Retain the source and backup as the rollback path until validation and cutover are approved; keep writers stopped while comparing.
5. Point `MONGODB_URI` and `MONGODB_DB` to the validated replica set, start the backend, check health and audit behavior, then resume writes. Do not write to both databases. After cutover, reverting requires accounting for new writes; simply reconnecting to the old standalone would lose them and this application rejects standalone topology.

## API

`POST /api/auth/login` accepts `{email,password}` and returns `{token,user}`. `GET /api/auth/me` requires a bearer token and returns public profile only. `POST /api/auth/password` accepts `{currentPassword,newPassword}` and returns a replacement token and user. Passwords must be 12–72 UTF-8 bytes; the current password must differ. `PUT /api/auth/landing` accepts `{defaultLandingPage: "dashboard" | "applications"}`. `POST /api/auth/logout` invalidates sessions. Before an administrator changes its initial password only profile, password change and logout are available. Each request verifies the current user is active. Login attempts and successful profile changes are audited; no credentials are written to audit records. Future protected business routes must depend on `unrestricted_user` to enforce the initial-password gate; `/me`, password change, logout and health are intentionally exempt.

## Portfolios

`GET /api/portfolios` accepts `search`, `status`, `productArea`, `limit` (1–100) and `offset`; it returns `{items,total,canCreate}`. Product-area filtering matches the portfolio's own `productArea` exactly, not the areas of its applications. `POST /api/portfolios`, `GET`/`PUT`/`DELETE /api/portfolios/{id}` and `GET /api/portfolios/{id}/applications` use bearer authentication. Names are unique; linked applications block deletion. Counts and rounded quality averages are calculated from applications, with null for no score. Administrators alone create or delete portfolios, and leaders may edit assigned portfolios; current role permissions must also grant the operation. Leaders, engineers and read-only users see only assignments. The seed inserts three portfolios and ten illustrative applications, and assigns the first portfolio to newly seeded scoped demo users without overwriting existing accounts. Application links navigate to application details.

## Executive dashboard

`GET /api/dashboard/executive` requires the current role's `view` permission and applies portfolio scope. Optional `portfolioId`, `productArea`, and `riskLevel` filter the applications; `limit` (1–100, default 25) and `offset` paginate only the portfolio breakdown, while scalar totals cover all matches. Without application filters, visible empty portfolios count; with product-area or risk filters, only portfolios containing matches count. Averages are rounded to the nearest integer and return null when no scores exist. The dashboard accepts a portfolio ID (available in portfolio URLs), product area, and risk level as filters.

## Administration and audit

Administrators with the current `administer` permission can manage local users and edit the six fixed roles at `/admin`. New or reset passwords must be 12–72 UTF-8 bytes and must be changed on next sign-in. `DELETE /api/users/{id}` deactivates the user and invalidates its session; audit history remains. Email is normalized to lowercase and unique. Assigned portfolios must exist. Empty assignments grant no portfolio access to leaders, engineers and read-only users; Administrator, Executive and Auditor retain cross-portfolio visibility. Role changes take effect on subsequent requests and remain subject to fixed role restrictions. Administrators must retain `administer`; transactional administration serializes checks for the last active administrator.

`GET /api/users` and `GET /api/roles` return bounded `{items,total}` pages; user creation, reading, editing and deactivation use `POST /api/users`, `GET`/`PUT`/`DELETE /api/users/{id}`, and role creation/editing use `POST /api/roles` and `PUT /api/roles/{id}`. The separate `/audit` page is read-only for Administrator and Auditor with `view`. `GET /api/audit-logs` supports `userId`, `action`, timezone-aware ISO `from` and `to`, `limit` and `offset`; `format=csv` exports the selected bounded page, requires current `export` permission and records an export event. CSV fields are protected against spreadsheet formula injection. Authentication, inventory and administration mutations commit with their audit events in MongoDB transactions. Audit failure aborts the mutation. Startup rejects standalone MongoDB and topologies without transaction-capable sessions; there is no non-transactional fallback.

## Reports and exports

`GET /api/reports/applications` and `/api/reports/portfolios` return `{items,total,canExport}` with the same filters and bounded pagination as their inventory lists. Application filters are `search`, `portfolioId`, `criticality`, `riskLevel`, and `lifecycleStatus`; portfolio filters are `search`, `status`, and `productArea`. `format=csv` exports **all** matching visible rows, ignoring `limit` and `offset`; the application repository export uses the same contract. Exports require both current `view` and `export` grants and a role allowed to export, and are audited. Text cells are escaped against spreadsheet formulas. Export audit is recorded separately from the response; it is not a transaction over the streamed output. Inventory changes during a multi-page export may affect its contents; it is not a point-in-time snapshot.

## Tests

The full backend suite requires **both** a disposable transaction-capable replica set and a separate disposable standalone MongoDB for fail-closed tests. With backend dependencies installed in an activated virtual environment, set:

```sh
export TEST_MONGODB_REPLICA_URI='mongodb://127.0.0.1:27017/?replicaSet=rs0&directConnection=true'
export TEST_MONGODB_STANDALONE_URI='mongodb://127.0.0.1:27018'
cd backend && python -m pytest -q
```

These are examples: run a separate standalone on port 27018 and use the correct URI for each deployment. `TEST_MONGODB_REPLICA_URI` selects the test replica; local fixtures default to `mongodb://127.0.0.1:27017/?replicaSet=rs0&directConnection=true` when it is unset. Set the replica URI explicitly for the full suite and for other replica configurations. `TEST_MONGODB_STANDALONE_URI` is mandatory for the standalone fail-closed tests. Tests create and drop uniquely named disposable databases; do not point them at valuable data. To run one module, use `python -m pytest -q tests/test_auth.py` from `backend` (or substitute `test_portfolios.py` or `test_dashboard.py`). Frontend component tests: `cd frontend && npm test`; typecheck and build: `cd frontend && npm run build`.

For E2E, start a transaction-capable MongoDB replica set and use a **fresh disposable** database. From `frontend`, set `E2E_ADMIN_PASSWORD` to the initial administrator password, then run `node node_modules/@playwright/test/cli.js test`. Playwright starts the backend and frontend with seeding enabled and a unique database name unless `E2E_MONGODB_DB` is supplied. Its default host URI is `mongodb://127.0.0.1:27017/?replicaSet=rs0&directConnection=true`, suitable for the Compose replica; override `E2E_MONGODB_URI` for another deployment. Remove the test database manually after the run. The journeys change the seeded password, landing preference and portfolio description and therefore must not be run against valuable data. Set `E2E_DEMO_PASSWORD` if the seeded demo password differs from the development default. Install Playwright Chromium first if needed: `node node_modules/@playwright/test/cli.js install chromium`.
